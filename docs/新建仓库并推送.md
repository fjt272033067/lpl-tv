# 新建仓库并推送 —— 可复用流程（含本机实测结论）

> 本文所有结论均在本机实测过（Windows + Git 2.52 + 中国内地电信 + Watt Toolkit 加速环境）。
> 2026-10-30 实测更正过一次早期误判：问题不在加速器，而在 **owner 拼写错误**。

---

## 0. 先做这一步：核对仓库真实全名

GitHub API 匿名可查，**不要凭记忆写账号名**：

```bash
# 账号是否存在（404 = 名字写错了，不是私有、不是限流）
curl -s https://api.github.com/users/<owner>
# 仓库是否存在、是否 Public
curl -s https://api.github.com/repos/<owner>/<repo>
# 名字拿不准时反查
curl -s "https://api.github.com/search/repositories?q=<repo>+in:name"
```

> GitHub 对「**不存在**」和「**存在但你无权限**」的仓库一律返回 **404**（刻意设计，防止探测私有仓库）。
> git 会把 404 翻译成 `Repository not found` —— **这几乎总是「owner 拼错」或「账号没权限」，不是网络问题。**

## 1. 新建仓库时的选项

| 选项 | 该怎么选 | 原因 |
|---|---|---|
| Repository name | 你的目标名 | |
| **Public / Private** | 取决于是否要**匿名读取**（见下） | 站点要匿名拉 raw JSON → **必须 Public**；私有仓的 raw 匿名请求一律 404 |
| **不要勾** README | 不勾 | 勾了远端会有初始 commit，与本地历史无共同祖先 → push 被拒 |
| **不要勾** .gitignore | 不勾 | 同上；本地的 .gitignore 才是权威 |
| **不要勾** LICENSE | 不勾 | 同上（本地想加再加） |

## 2. 推送：完整流程

### 2.1 完整命令（全新项目）

```bash
# 1. 本地初始化（若已是仓库则跳过）
git init

# 2. 提交代码（先确认 .gitignore 已就位，见 2.3）
git add .
git commit -m "init: 首次提交"

# 3. 关联远端并推送
git remote add origin https://github.com/<owner>/<repo>.git
git branch -M main
git push -u origin main
```

### 2.2 三个容易踩的细节

| 细节 | 说明 |
|---|---|
| `git push` 推的是**完整历史**，不只是最后一次提交 | 本地 24 个提交会**全部**推上去、**全部**公开。改代码擦不掉历史 —— 提交过一次再删文件也没用 |
| `git branch -M main` 的大写 **M = 强制** | 若本地已有 `main` 分支，会被**覆盖**。分支改名用小写 `git branch -m main` 更安全 |
| `git add .` 会把**所有**未被忽略的文件都加上 | 大文件、临时产物、`.env`、密钥文件统统会被提交 —— 推之前必须先看 `.gitignore` |

### 2.3 `.gitignore` 自查

推送前确认至少忽略这些：

```gitignore
node_modules/
dist/
build/
.env
.env.*
*.log
*.pem
*.key
.DS_Store
```

### 2.4 推送前 30 秒体检清单

```bash
git status --short                 # ① 有没有该忽略却没忽略的东西
git ls-files | wc -l               # ② 文件数是否合理
git log --oneline | wc -l          # ③ 提交数
git count-objects -vH | grep size  # ④ 仓库体积
git ls-files | xargs ls -lS 2>/dev/null | head -5   # ⑤ 最大的 5 个被跟踪文件
```

本项目实测（2026-10-30）：24 提交 / 241 文件 / 弹幕目录 16.7MB / 单文件最大 0.58MB。

### 2.5 两条路

**路径 A · HTTPS（通用，换任何机器都能用）**

```bash
git remote add origin https://github.com/<owner>/<repo>.git
git branch -M main
git push -u origin main
```

- 首次 push 会弹**浏览器授权窗口**（Git Credential Manager），点一下授权，凭据会被记进 Windows 凭据管理器，之后不再弹。
- 不想用浏览器授权，就改用 **fine-grained PAT**（仓库 → Settings → Developer settings → Personal access tokens，勾 `Contents: Read and write`）。
- 已有 remote 要改地址：`git remote set-url origin <新地址>`。

**路径 B · SSH（本机已配好，更省事，无需浏览器）**

本机 `~/.ssh/config` **已经配好**（见下方附录），换任何项目都直接用：

```bash
git remote add origin git@github.com:<owner>/<repo>.git
git branch -M main
git push -u origin main
```

公钥必须注册在**拥有该仓库的那个账号**下 —— 加错账号的表现和 owner 拼错一模一样（404 → Repository not found）。

### 2.6 ⚠️ 定时调度压根没注册（`event=schedule` 零 run）—— 实测踩坑全过程

**症状极具误导性：其它一切正常，唯独定时不跑，而且不报错、不发邮件。**

| 现象 | 是否正常 |
|---|---|
| workflow 在 Actions 里显示 `active` | ✅ 正常 |
| `workflow_dispatch` 手动触发能跑 | ✅ 正常 |
| `push` 触发器照常触发 | ✅ 正常 |
| `event=schedule` 的 run **一条都没有** | ❌ 就是这个问题 |

**本项目 2026-10-30 的完整排查链（照这个顺序做，不要跳步）**：

```bash
# ① 确认工作流文件确实在默认分支上、YAML 合法、cron 是合法 5 段 POSIX
git show origin/main:.github/workflows/<你的工作流>.yml | grep -n "cron:\|schedule:\|^on:"
# ② 确认仓库状态：公开、非 fork、未归档、默认分支正确
curl -s https://api.github.com/repos/<owner>/<repo> | grep -E 'default_branch|visibility|fork|archived'
# ③ 看调度到底有没有跑过
curl -s "https://api.github.com/repos/<owner>/<repo>/actions/runs?event=schedule"
# ④ 平台是否健康（用一个已知在跑定时任务的公开仓库当对照组）
curl -s "https://api.github.com/repos/github/docs/actions/runs?event=schedule&per_page=3"
```

**曾经误判过的一个根因（写下来是为了别再走一遍）**：
本仓库当时 `git config user.email` 是 `fangchen@localhost` —— 这个地址在 GitHub 上
不对应任何账号，提交在 API 里顶层 `author.login` / `committer.login` 全是 `null`。
当时的结论是「GitHub 的调度绑定到最后一次修改 cron 那行提交的身份，归属不到账号就不注册」，
于是把身份改成 noreply 邮箱、又改了一次 cron 强制重注册。

**结果：修完之后依然是零 schedule run。** 所以那条「绑定提交身份」的机制**至少不是根因**
（GitHub 官方文档里并没有这条规则）。身份该改还是要改（它本身是最佳实践，也避免
API 里出现一堆 `null` 提交者），但**别把它当成调度不注册的根因**。

**真正的判决手段：加一个最小探针工作流**，把「仓库层面」和「工作流文件层面」分开：

```yaml
# .github/workflows/_cron-probe.yml —— 临时用，结论出来就删掉
name: cron-probe
on:
  schedule:
    - cron: '*/5 * * * *'
  workflow_dispatch:
jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - run: echo "probe $(date -u)"
```

推上去，等 15 分钟，看 `event=schedule` 里有没有 `cron-probe`：

| 探针结果 | 含义 | 下一步 |
|---|---|---|
| 探针有 schedule run，但你的工作流没有 | 你的工作流文件本身有问题 | 回头查 YAML / cron 表达式 |
| 探针**也没有** schedule run | **仓库/账号层面的调度没注册** | 换触发通道 → 见 2.7 |

本项目实测：探针也没有（06:00 / 06:05 / 06:10 / 06:15 四槽全空），
而同一时刻对照组 `github/docs` 有 2500 条 schedule run（最近一条就在几小时前），
`push` / `workflow_dispatch` 全部正常，仓库公开、非 fork、未归档、默认分支 main。
→ 结论：**GitHub 的调度器对本仓库不工作**，不是配置写错。

**另一个连带风险**：公开仓库 60 天没有活动，GitHub 会**自动停用**定时工作流
（仓库越安静越容易触发，因为 cron 自己产生的提交不算活动）。
有定期活动就不受影响；真被停用时 Actions 页会有横幅和 "Enable workflow" 按钮。

### 2.7 定时调度不可用时的替代通道：外部调度器 + fine-grained PAT

既然 `schedule` 靠不住，就用**外部调度器**打 GitHub 的 dispatch 接口。
这条通道完全在云端，**不需要你的桌面端跑任何定时任务**。

**① 建一个最小权限的 PAT**
（<https://github.com/settings/personal-access-tokens/new>）

- Repository access：Only select repositories → 只勾目标仓库
- Repository permissions → **Actions: Read and write**
- 生成后复制（形如 `github_pat_xxx`），**只粘到调度服务里，不要提交进仓库**

**② 在任意免费定时服务里加一条 HTTP 任务**
（cron-job.org / UptimeRobot / 一台小 VPS 的 crontab 都行，都不要本机常驻）

```
POST https://api.github.com/repos/<owner>/<repo>/actions/workflows/<workflow>.yml/dispatches
Authorization: Bearer <你的 PAT>
Content-Type: application/json

{"ref":"main"}
```

每 20 分钟一次即可。

**③ 手动触发同一条通道（调试用）**

```bash
$env:GITHUB_TOKEN = 'github_pat_xxx'
node tools/dispatch-refresh.mjs      # 本仓库已内置这个脚本
```

**④ 备用事件**：`repository_dispatch`（需要 `Contents: Read and write`）

```bash
curl -X POST https://api.github.com/repos/<owner>/<repo>/dispatches \
  -H "Authorization: Bearer <PAT>" -H "Content-Type: application/json" \
  -d '{"event_type":"refresh-data"}'
```

**不要用「工作流自己 dispatch 自己」来自续命**：`GITHUB_TOKEN` 触发的
`workflow_dispatch` 确实能再排一个 run，但那等于把 Actions 当成常驻计算服务用，
既踩 GitHub 的使用条款，又要靠空转 runner 来控制节奏。

## 3. 推送后自检

```bash
git ls-remote origin                      # 能列出 refs = 链路 + 地址 + 权限都 OK
git log --oneline -1 origin/main          # 远端 HEAD 和本地一致
```

如果 `git ls-remote` **列不出来**：

| 报错 | 含义 | 怎么办 |
|---|---|---|
| `Repository not found` | owner 拼错 **或** 该账号无此仓库权限 | 回第 0 步核对名字 |
| `could not read Username ... terminal prompts disabled` | 缺凭据（非交互 shell 专有） | 在交互终端里跑，或用 SSH |
| `Invalid username or token` | 凭据无效/过期 | 删掉旧凭据重新授权，或改用 SSH |
| 连接超时 | 网络/加速器问题 | 见下方「本机网络注意事项」 |

## 4. 本机网络注意事项（内地电信 + Watt Toolkit）

本机 `hosts` 把 `github.com` / `api.github.com` / `raw.githubusercontent.com` 等
全部指向 `127.0.0.1`，**Steam++ 同时监听 80 和 443 并正确代理 HTTPS** ——
实测开着加速器 `git ls-remote` 对公开仓库**能正常返回 refs**，所以
**git 报错不要先归咎加速器**。

- 需要**真直连** GitHub（大仓库 clone、release/大文件下载）时，
  **先提示使用者退出 Watt Toolkit**；**下载优先走国内镜像源**（ghproxy、npmmirror、gitee 镜像、gitclone）。
- `ssh.github.com` 不在 hosts 名单里，能直连（22 / 443 均通），属于**直连**——大流量推送会很慢，用之前先说明。

## 5. 如果新项目也要「站点自动读远端数据」

光推代码不够，还要让**站点**指向这个仓库：

```bash
node tools/set-data-base.mjs https://raw.githubusercontent.com/<owner>/<repo>/main/site/data
node tools/stamp-assets.mjs          # 给资源 URL 挂内容哈希戳，绕开 CDN 的旧缓存
# 然后重新部署 site/ 目录
```

### 5.1 必须配「多个镜像」，而且要按文件设「陈旧上限」

**为什么要镜像**（实测 2026-10-30，本机 Chrome 里的真实结果）：

| 托管 | 缓存策略 | 大陆可达 | 结论 |
|---|---|---|---|
| `raw.githubusercontent.com` | `max-age=300` + `ACAO: *` | ❌ 本机浏览器 8ms 就 `Failed to fetch` | 主源，但别只押它 |
| `gh-proxy.com/https://raw.githubusercontent.com/...` | `max-age=60` + `ACAO: *` | ✅ 1166ms 拿到**最新**内容 | **实时备用源，实测最靠谱** |
| `cdn.jsdelivr.net` / `gcore` / `fastly` | `s-maxage=43200`（**12 小时**） | ✅ | 只能当慢变数据的兜底 |

两个坑：

1. **浏览器不继承系统代理**。本机 hosts 把 `raw.githubusercontent.com` 指到 `127.0.0.1`，
   PowerShell 走系统代理能通（1062ms），**同一个地址在 Chrome 里 8ms 就失败**。
   所以「我用命令行能拉到」**推不出**「用户浏览器能拉到」。
2. **jsDelivr 的 12 小时缓存是硬伤**：仓库提交 34 分钟后它还在吐旧版本
   （实测 `version.json` 停在 `05:28`，仓库最新已是 `06:02`）。
   分支 URL 后面加 `?v=xxx` 也**破不掉**它的缓存（`age` 头没变）。

**所以站点侧必须是三件事一起做**：

- **多镜像并发探测**：每个镜像各自独立结算（不等最慢的那个 ——
  否则一个卡住的镜像会把整条探测拖死）；
- **按内容时间戳挑最新的那份**，而不是「第一个返回的」——
  镜像的新鲜度差一个数量级，先到的不一定最新；
- **按文件设陈旧上限**：超过上限就不采用远端那份。
  B 站流地址约 60 分钟过期 → `liverooms` 上限设 **75 分钟**（TTL + 余量）；
  赛程 / 录像目录本来就慢变 → 上限 24 小时。
  少了这条，一个 12 小时缓存的镜像会让页面「看着有内容、播放器却是黑的」。
  ⚠️ 上限别设太宽：2 小时虽然「更宽容」，但也够把一份 90 分钟前的
  过期流地址放进播放器了 —— 75 分钟卡在 TTL 之上、余量之下。

**外加一条：镜像的失败退避要按次数递进，别一刀切记死。**
原来「失败一次 → 跳过 30 分钟」，而 `raw.githubusercontent.com` 偶发失败一次
（本机 Chrome 8ms 就 `Failed to fetch`）—— 于是**唯一新鲜的源**整整半小时
不参与探测，站点只能拿到落后 15 分钟的代理缓存，数据更新链直接断一截。
→ 失败 1 次只跳过 1 分钟（探测周期就是 1 分钟）、2 次 5 分钟、再往后 30 分钟；
成功一次即清零。

### 5.2 远端绝不能挡住首屏，但也不能静默失败

- **不 await 远端探测**：本地快照先渲染，远端在后台探测，拿到更新的数据再自动升级重绘。
  （后台标签页里 Chrome 会节流 `setTimeout`，探测的超时可能迟迟不触发，
  那个 Promise 永远不 resolve，整页卡在「正在加载…」。这个坑真的踩过。）
- **升级回调不能丢**：探测返回时页面可能还没注册回调 → 用一个 `pendingUpgrade` 标志兜住，
  谁后注册谁接手。否则这次升级会被静默丢掉，页面永远停在旧数据上。
- **远端探不通要重试 + 明说**：每 45 秒重试；页面挂一条横幅写清楚
  「当前显示的是 N 分钟前的本地快照」，而不是让「暂无直播信号」这种含糊提示去背锅。
- **判据也跟着改**：上游在播却没显示出来 **且** 没有告知通道故障，才算失败。

### 5.3 验收要「信号感知」

直播页的判据不能写死「必须有清晰度档位」—— 休赛期本来就没信号。
正确做法：先在 Node 侧独立问上游「现在有没有直播信号」，
再据此决定页面应该显示什么；上游在播却显示不出来才算回归。
本地套件还要把**所有镜像**都拦掉（`ctx.route`），否则镜像竞速会打到网络，判据会飘。

### 5.4 「限制类」判据必须有反向对照，否则它可能永远为真

给站点加了限制（陈旧上限、大小上限、数量上限…）之后，
配套的验收判据很容易写成一句**永远为真**的话：

> 「90 分钟前的远端直播源不会被采用」—— 可要是页面**根本没去读远端**呢？

所以这类判据必须配一个**反向对照场景**，把限制临时放宽，验证它确实会变：

| 场景 | 远端 liverooms 的时间戳 | 上限 | 期望 |
|---|---|---|---|
| A 对照 | 10 分钟前 | 75 分钟 | **采纳远端** |
| B 被测 | 90 分钟前 | 75 分钟 | **拒绝远端**，回退本地 + 弹「快照已过期」 |
| C 反向对照 | 90 分钟前 | 24 小时（临时改） | **采纳远端** |

- A 证明「正常情况下远端确实会被采用」（否则 B 的「拒绝」可能只是通道根本没通）；
- C 证明「B 的拒绝确实是上限造成的」（否则 B 可能只是页面没去读远端）。

实现要点：C 用 `page.route` 把 `assets/app.js` 改掉后 `fulfill` 回去，
**只在这一页生效、不碰仓库文件**；改完要断言 `patched !== src`，
否则源码里的常量一旦改名，对照场景会静默退化成「没改」，
判据就失去判别力了。

顺带一条：拒绝远端时**页面不能装作没事**——
横幅要区分「通道不可达」和「直播源快照已过期」，
后者要明确告诉用户「暂无直播信号多半不是赛事没开，而是数据太旧」。

```
Host github.com
```

```bash
ssh-keygen -t ed25519 -C "<你的标签>" -f "$env:USERPROFILE\.ssh\id_ed25519_<新项目>"
```

```bash
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
```

**必须加在拥有该仓库的账号下**。
