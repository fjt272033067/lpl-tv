- **~~关键事实：开赛 1 小时后 `ScoreA/ScoreB` 仍是 `"0"`。该字段疑似只在局间/局末更新，或国际赛事不更新。~~**
  **❌ 这条判断已于 2026-11-15 05:19 被实测推翻 —— 真相是「边缘节点滞后副本」，不是上游不更新。**
  复核证据（同一出口、四个请求变体：直连 / 加随机查询串 / `?v=2`）：
  ```
  Last-Modified 全部 = Sat, 14 Nov 2026 20:35:13 GMT    Age=88   Cache-Control: max-age=60
  比分 = GEN vs BLG 1:0
  ```
  腾讯这张表**确实会更新**（0:0 → 1:0，Last-Modified 证明 20:35 就在发）。
  更准确的表述：**同一时刻不同出口/边缘可能拿到不同版本的副本**；
  `max-age=60` + 各边缘刷新节奏不同 → 滞后几十秒到几十分钟。
  → **教训**：看到「数据长时间不变」时，**先怀疑自己命中了陈旧副本**（对比 Last-Modified / 换出口 / 多镜像交叉验证），
  **不要**直接断言「上游不更新」。这是本项目最容易误判的一类证据。

**自动解读文案**（基于历史数据生成，不编数字）：
- GEN：S16 5 战全胜、小局 10-1、两个 BO5 全 3:0 **零封** → 「零封率 100%」
- BLG：5-2、小局 11-4、BO5 丢过 1 小局、BO5 胜率更低但对手更硬（TES/HLE/T1/DK）、多休 1 天
- 历史零交手 → 「首次交手，历史数据无先验」
- 赛制：BO5，3 胜制

### B. 胜率概率预测（P0）

**模型（可解释、可手算、前端零依赖）**：

1. **赛前先验**：`P(GEN) = 0.55 / P(BLG) = 0.45`
   依据：GEN 赛季 5-0 / 小局 10-1 / BO5 全零封；BLG 5-2 / 小局 11-4 / 打过更多硬队。
   **必须在 UI 上写明这是基于哪几个输入算的**，不要装作精密模型。
2. **小局胜率**：从 S16 淘汰赛 BO5 反推每队单小局胜率
   - GEN：两个 BO5 均 3:0 → 单小局极强
   - BLG：BO5 3:0 + 3:1 → 单小局胜率略低于 GEN
   （具体数值由新会话从 `schedule.json` 里 GEN/BLG 所有 BO5 记录实算，**不要手填**。）
3. **实时条件更新**：已知当前大比分 `a:b`，BO5 剩余局数 → 用每小局胜率 `p` 做
   `P(GEN) = Σ C(n,k) p^k (1-p)^(n-k)`（n = 3 - max(a,b) 局，k = 3-a 局）
   → 胜率条随比分实时跳变。
4. **终局归一**：3:0 → 100% / 0:3 → 0% / 3:1 → 100% 等。
5. **可解释性**：胜率条下方显示「当前 1:0 · 剩余需 2 胜 · 单小局 p=0.64 → 62%」这种推导链。

**验收断言（新增）**：
- 概率恒在 [0,1]；随 GEN 领先局数**单调不减**
- 3:0 → 100%，0:3 → 0%
- 与赛前先验 55/45 在 0:0 时一致（不允许凭空改先验）
- 模型输入全部来自数据文件，**禁止硬编码编造的历史数字**

## 4. 铁律（继承上一任，全部踩过坑）

### 4.1 架构
- 纯静态、零后端、**零外部运行时依赖**
- ❌ 不用公开 CORS 代理 ❌ 不嵌 iframe ❌ 不转存视频/弹幕到服务器
- 数据更新**只靠外部 CI**（用户明确拒绝桌面端定时任务）
- 同一 `node_id` 原地发布是既定工作流；主/别名 URL 保持不变

### 4.2 浏览器
- **干活时不要在本机弹浏览器窗口**（用户明确纠正过）
- 所有脚本默认无头；需要人眼看才 `HEADED=1`
- **浏览器不继承系统代理** → 镜像可达性必须浏览器内实测

### 4.3 验收

## 8. ⚠️ 基线验收是 99/101，不是 101/101（已定位：判据缺陷，非线上回归）

原会话在 04:1x 跑了 `node tools/verify.mjs`，结果 **99/101**，2 项 FAIL：

```
✗ 陈旧快照下未开打对阵标为「待确认」  pending=0
✗ 赛程快照时间在 48 小时内              滞后 134 小时
```

### 根因一：「赛程快照时间在 48 小时内」—— 判据读错字段

- `tools/verify.mjs:1867` 读 `local.updatedAt` = **schedule.json 的 updatedAt**（2026-11-09T06:26:55Z）
- 但**线上页面读的是 `version.json.updatedAt`**（2026-11-14T19:59:09Z = 核对时间）→ 线上显示新鲜，**线上行为正确**
- schedule.json 的 updatedAt 之所以冻结：`.github/workflows/refresh-data.yml:27` 明确写着
  「bake.mjs 只在『内容真的变了』时才更新 schedule/catalog 的 updatedAt」
  → 它的语义是**上游内容最后变化时间**，不是核对时间。腾讯自 11-09 起赛程内容没变 → 停在 11-09
- **修法**：改断言 `version.json.updatedAt` 在 48 小时内；可另加一条允许 `schedule.updatedAt <= version.updatedAt`

### 根因二：「陈旧快照下未开打对阵标为『待确认』」—— 场景已失效

`site/assets/app.js:4143`：

```js
const unconfirmed = fresh.stale && !done2 && !s.live && st > now - 2 * 3600000;
```

- `fresh.stale` 是**单一布尔**，banner 与 unconfirmed 共用 → banner 那条 PASS 说明陈旧构造**生效了**
- 失败在 `!s.live`：决赛被腾讯实时数据 overlay 成**正在直播**（`s.live=true`）
  → 按设计**不**标「待确认」（实时数据是权威的，标「待确认」反而是错信息）
- 这条判据原为「休赛期存在远期未开打场次」设计；决赛一开打，场景就不存在了
- **修法**：构造里**注入**一条确定的未来未开打且非直播的假场次（别依赖真实数据恰好有）

### 处置原则

**不要为此改 `app.js`** —— 线上运行时是对的，改了会引入真回归。
这正好是本项目铁律的反例：

1. 判据不得依赖数据年龄（数据会漂移，须按实际状态分情况断言或注入构造数据）
2. 分文件判龄口径：schedule/catalog 看 `version.json.updatedAt`；liverooms 看内容时间戳
