# 附录 · 定时调度与数据通道排查

> **给谁看**：需要深入排查的人（改代码的人、AI 助手、以后接手这个项目的人）。
> 日常运维操作看 **`新建仓库并推送.md`** 就够了，本文只记录「为什么这么做」的实测过程。
>
> 所有结论均在 **Windows + Git 2.52 + 中国内地电信 + Watt Toolkit 加速环境**下实测过。
> 2026-10-30 实测更正过一次早期误判：问题不在加速器，而在 **owner 拼写错误**。

## 1. 先核对仓库真实全名

GitHub API 匿名可查，**不要凭记忆写账号名**：

```bash
# 账号是否存在（404 = 名字写错了，不是私有、不是限流）
curl -s https://api.github.com/users/<owner>
# 仓库是否存在、是否 Public
curl -s https://api.github.com/repos/<owner>/<repo>
# 名字拿不准时反查
curl -s "https://api.github.com/search/repositories?q=<repo>+in:name"
```

> GitHub 对「**不存在**」和「**存在但你无权限**」的仓库一律返回 **404**（刻意设计，防止探测私有仓库）。
> git 会把 404 翻译成 `Repository not found` —— **这几乎总是「owner 拼错」或「账号没权限」，不是网络问题。**
>
> 真实踩坑：某次交付把账号名写成 `fj272033067`（少一个 `t`），真实账号是 `fjt272033067`。
> GitHub API 对不存在的账号返回 404，很容易被误读成「仓库是私有的」或「网络问题」。
> 更糟的是这个错名字被烧进了已上线的站点 HTML，导致站点永远读不到远端数据，
> 而「站点能正常打开」完全掩盖了它。
>
> **通则**：凡是「凭记忆写下的账号名/仓库名/域名」都是高风险输入，
> **以一次 API 核实为准**，而不是以之前会话的记录为准。

## 2. 定时调度压根没注册（`event=schedule` 零 run）—— 实测踩坑全过程

**症状极具误导性：其它一切正常，唯独定时不跑，而且不报错、不发邮件。**

| 现象 | 是否正常 |
|---|---|
| workflow 在 Actions 里显示 `active` | ✅ 正常 |
| `workflow_dispatch` 手动触发能跑 | ✅ 正常 |
| `push` 触发器照常触发 | ✅ 正常 |
| `event=schedule` 的 run **一条都没有** | ❌ 就是这个问题 |

### 2.1 完整排查链（照这个顺序做，不要跳步）

```bash
# ① 确认工作流文件确实在默认分支上、YAML 合法、cron 是合法 5 段 POSIX
git show origin/main:.github/workflows/<你的工作流>.yml | grep -n "cron:\|schedule:\|^on:"
# ② 确认仓库状态：公开、非 fork、未归档、默认分支正确
curl -s https://api.github.com/repos/<owner>/<repo> | grep -E 'default_branch|visibility|fork|archived'
# ③ 看调度到底有没有跑过
curl -s "https://api.github.com/repos/<owner>/<repo>/actions/runs?event=schedule"
# ④ 平台是否健康（用一个已知在跑定时任务的公开仓库当对照组）
curl -s "https://api.github.com/repos/github/docs/actions/runs?event=schedule&per_page=3"
```

### 2.2 曾经误判过的根因（写下来是为了别再走一遍）

本仓库当时 `git config user.email` 是 `fangchen@localhost` —— 这个地址在 GitHub 上
不对应任何账号，提交在 API 里顶层 `author.login` / `committer.login` 全是 `null`。
当时的结论是「GitHub 的调度绑定到最后一次修改 cron 那行提交的身份，归属不到账号就不注册」，
于是把身份改成 noreply 邮箱、又改了一次 cron 强制重注册。

**结果：修完之后依然是零 schedule run。** 所以那条「绑定提交身份」的机制**至少不是根因**
（GitHub 官方文档里并没有这条规则）。身份该改还是要改（它本身是最佳实践，也避免
API 里出现一堆 `null` 提交者），但**别把它当成调度不注册的根因**。

### 2.3 真正的判决手段：加一个最小探针工作流

把「仓库层面」和「工作流文件层面」分开：

```yaml
# .github/workflows/_cron-probe.yml —— 临时用，结论出来就删掉
name: cron-probe
on:
  schedule:
    - cron: '*/5 * * * *'
  workflow_dispatch:
jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - run: echo "probe $(date -u)"
```

推上去，等 15 分钟，看 `event=schedule` 里有没有 `cron-probe`：

| 探针结果 | 含义 | 下一步 |
|---|---|---|
| 探针有 schedule run，但你的工作流没有 | 你的工作流文件本身有问题 | 回头查 YAML / cron 表达式 |
| 探针**也没有** schedule run | **仓库/账号层面的调度没注册** | 换触发通道 → 见 §2.4 |

**本项目实测**：探针也没有（06:00 / 06:05 / 06:10 / 06:15 四槽全空），
而同一时刻对照组 `github/docs` 有 2500 条 schedule run（最近一条就在几小时前），
`push` / `workflow_dispatch` 全部正常，仓库公开、非 fork、未归档、默认分支 main。
→ 结论：**GitHub 的调度器对本仓库不工作**，不是配置写错。

### 2.4 替代通道（云端、不需要本机常驻）

外部定时服务打 dispatch 接口（cron-job.org / UptimeRobot / 小 VPS 的 crontab 都行）：

```
POST https://api.github.com/repos/<owner>/<repo>/actions/workflows/<workflow>.yml/dispatches
Authorization: Bearer <fine-grained PAT>     # Actions: Read and write，仅限该仓库
Content-Type: application/json
{"ref":"main"}
```

备用事件 `repository_dispatch`（需 `Contents: Read and write`）：
`POST /repos/<owner>/<repo>/dispatches`，体 `{"event_type":"refresh-data"}`。

**不要用「工作流自己 dispatch 自己」自续命**：`GITHUB_TOKEN` 触发的 `workflow_dispatch`
确实能再排一个 run，但等于把 Actions 当常驻计算服务（踩使用条款），且要靠空转 runner 控制节奏。

### 2.5 同一类根因的其他变体（GitHub 社区反复出现）

- workflow 不在默认分支 → 永不触发
- 是 fork → 定时默认关闭
- 公开仓库 60 天无活动 → GitHub 自动停用定时工作流（cron 自身的提交**不算**活动）
- cron 表达式必须是 5 字段 POSIX 且**加引号**（裸 `*` 会被 YAML 当 alias）
- `@daily` / `@hourly` 等宏不支持

**通用教训**：GitHub Actions 的「静默失败」几乎都在**事件创建阶段**，不是 job 执行阶段 ——
没有 run 记录 = 没有 run 日志可查，此时改 job 步骤或 runner 配置都是白费力气，
要查的是「事件有没有被创建」。

## 3. 静态站的「远端数据通道」必须多镜像 + 按文件设陈旧上限

### 3.1 镜像实测结果（本机 Chrome 里的真实数据）

| 托管 | 缓存策略 | 大陆可达 | 结论 |
|---|---|---|---|
| `raw.githubusercontent.com` | `max-age=300` + `ACAO: *` | ❌ 本机浏览器 8ms 就 `Failed to fetch` | 主源，但别只押它 |
| `gh-proxy.com/https://raw.githubusercontent.com/...` | `max-age=60` + `ACAO: *` | ✅ 能拿到内容 | 实时备用源，实测最靠谱 |
| `cdn.jsdelivr.net` / `gcore` / `fastly` | `s-maxage=43200`（**12 小时**） | ✅ | 只能当慢变数据的兜底 |

### 3.2 两个坑

1. **浏览器不继承系统代理**。本机 hosts 把 `raw.githubusercontent.com` 指到 `127.0.0.1`，
   PowerShell 走系统代理能通（1062ms），**同一个地址在 Chrome 里 8ms 就失败**。
   所以「我用命令行能拉到」**推不出**「用户浏览器能拉到」。
   → 站点要并发探测**多个镜像**，并且**按内容时间戳挑最新的那份**，
   不是「第一个返回的就算数」。
2. **jsDelivr 的 12 小时缓存是硬伤**：仓库提交 34 分钟后它还在吐旧版本
   （实测 `version.json` 停在 `05:28`，仓库最新已是 `06:02`）。
   分支 URL 后面加 `?v=xxx` 也**破不掉**它的缓存（`age` 头没变）→ 只能作慢变数据兜底。

### 3.3 所以站点侧必须是三件事一起做

- **多镜像并发探测**：每个镜像各自独立结算（不等最慢的那个 ——
  否则一个卡住的镜像会把整条探测拖死）；
- **按内容时间戳挑最新的那份**，而不是「第一个返回的」——
  镜像的新鲜度差一个数量级，先到的不一定最新；
- **按文件设陈旧上限**：超过上限就不采用远端那份。
  B 站流地址约 60 分钟过期 → `liverooms` 上限设 **75 分钟**；
  赛程 / 录像目录本来就慢变 → 上限 24 小时。
  ⚠️ 上限别设太宽：2 小时虽然「更宽容」，但也够把一份 90 分钟前的
  过期流地址放进播放器了 —— 75 分钟卡在 TTL 之上、余量之下。

**外加一条：镜像的失败退避要按次数递进，别一刀切记死。**
原来「失败一次 → 跳过 30 分钟」，而 `raw.githubusercontent.com` 偶发失败一次
（本机 Chrome 8ms 就 `Failed to fetch`）—— 于是**唯一新鲜的源**整整半小时
不参与探测，站点只能拿到落后 15 分钟的代理缓存，数据更新链直接断一截。
→ 失败 1 次只跳过 1 分钟（探测周期就是 1 分钟）、2 次 5 分钟、再往后 30 分钟；
成功一次即清零。

**镜像之间会「互相遮蔽」**：代理型镜像（gh-proxy.com）自己的边缘缓存虽然写着
`max-age=60`，但它上游取到的 raw 副本是旧的 → 实测它稳定落后 15-25 分钟；
jsDelivr 落后 12 小时。→ 站点必须**全部探测 + 按内容时间戳择新**。

### 3.4 远端绝不能挡住首屏，但也不能静默失败

- **不 await 远端探测**：本地快照先渲染，远端在后台探测，拿到更新的数据再自动升级重绘。
  （后台标签页里 Chrome 会节流 `setTimeout`，探测的超时可能迟迟不触发，
  那个 Promise 永远不 resolve，整页卡在「正在加载…」。这个坑真的踩过。）
- **升级回调不能丢**：探测返回时页面可能还没注册回调 → 用一个 `pendingUpgrade` 标志兜住，
  谁后注册谁接手。否则这次升级会被静默丢掉，页面永远停在旧数据上。
- **变量声明必须早于回调注册**，否则会 TDZ ReferenceError（升级回调可能在
  `renderLive` 的 await 期间触发）。
- **远端探不通要重试 + 明说**：每 45 秒重试；页面挂一条横幅写清楚
  「当前显示的是 N 分钟前的本地快照」，而不是让「暂无直播信号」这种含糊提示去背锅。
- **远端数据更新不打断正在播放的线路**：只在当前流地址失效时才整页重绘。
- **通道状态要可观测**：做成 `window.__LPLTV_DATA_STATUS__`
  （`state: unknown|ok|failed`、生效基址、origin、失败原因），
  页面挂横幅 + 「重新拉取」按钮，探不通就每 45 秒重试（页面不可见时不重试）。

### 3.5 验收要「信号感知」

直播页的判据不能写死「必须有清晰度档位」—— 休赛期本来就没信号。
正确做法：先在 Node 侧独立问上游「现在有没有直播信号」，
再据此决定页面应该显示什么；上游在播却显示不出来才算回归。
本地套件还要把**所有镜像**都拦掉（`ctx.route`），否则镜像竞速会打到网络，判据会飘。

### 3.6 「限制类」判据要配反向对照，否则它可能永远为真

给站点加了限制（陈旧上限、大小上限、数量上限…）之后，配套验收很容易写成一句永远为真的话：
「90 分钟前的远端直播源不会被采用」—— 可要是页面**根本没去读远端**呢？

**规则：** 每加一条「限制类」判据，配三个场景：

| 场景 | 远端 liverooms 的时间戳 | 上限 | 期望 |
|---|---|---|---|
| A 对照 | 10 分钟前 | 75 分钟 | **采纳远端** |
| B 被测 | 90 分钟前 | 75 分钟 | **拒绝远端**，回退本地 + 弹「快照已过期」 |
| C 反向对照 | 90 分钟前 | 24 小时（临时改） | **采纳远端** |

- A 证明「正常情况下远端确实会被采用」（否则 B 的「拒绝」可能只是通道根本没通）；
- C 证明「B 的拒绝确实是上限造成的」（否则 B 可能只是页面没去读远端）。

实现要点：
1. C 用 `page.route` 改写被测资源后 `fulfill` 回去 —— **只在该页生效，不改仓库文件**；
2. 改完要断言「确实改动了」（如 `patched !== src`），否则源码里的常量一旦改名，
   对照会静默退化成「没改」，判据就失去判别力了；
3. 注入/改写类 route 一律用**函数式匹配 + 主机/端口白名单**，别用裸通配符
   （本地站和假远端服务器可能同主机不同端口）。

**证据：** 2026-10-30 lpl-tv「liverooms 陈旧上限 75 分钟」判据
（`tools/verify.mjs` 83 → 88 项）。场景 C 实测：上限临时改成 24h 后，
同一份 90 分钟前的远端确实被采纳（`liveUpdatedAt` 从本地戳变成远端戳）→ B 的判据有判别力。

**推论：** 「限制类」与「存在性类」判据要区别对待 —— 存在性判据（"页面必须有清晰度档位"）
只需一个对照场景即可；限制类判据**必须**有 C，否则很可能是一条空断言。

### 3.7 静态站：渲染「清空 + 回填」中间有 await → 并发渲染交错 → 页面内容重复

**症状**：SPA 里同一个页面出现**两份内容**（新的在上面、旧的在下面，往下滚能看到）。

**根因**：渲染流程是「先 `view.innerHTML = ''` 清空 → `await` 若干 → 逐块 `view.appendChild` 回填」。
清空与回填之间只要有 await，两个渲染就会交错。

**修法（三层一起上）**：
1. **渲染代次守卫**：`beginRender()` 领号，`isStaleRender(seq)` 判断；过期渲染**直接 return，一个 DOM 都不碰**。
   - 守卫要放在**两个点**：①清空之前 ②最终挂载之前。只守一个不够 ——
     过期渲染若能清空，会把新渲染的内容抹掉。
2. **清空与回填原子化**：把所有 await 前移到 `view.innerHTML = ''` 之前。
   - ⚠️ 但只在「await 之后的产物不直接进 view」时才能这么做；否则把慢调用前移会**阻塞首屏**。
     更稳的做法是「离屏容器构建 + 挂载前守卫」。
3. **静态 lint**：写个脚本扫「`view.innerHTML = ''` 之后还有没有 await」，有就报出来，可挂 CI。
   （本仓库：`tools/check-render-races.mjs`）

**通用判据**：凡是「清空 → await → 追加」三段式渲染，await 必须在最外层：
要么全前移，要么把挂载点收敛成一个并加守卫。

## 4. CI 提交步骤的 `git pull --rebase || true` → push 退出码 128（静默丢数据）

**症状**：连续两次 CI 触发器跑同一仓库，**第二轮失败**，Actions 页面只显示
`Process completed with exit code 128`，日志里看不出任何原因。

**根因链**：
1. `actions/checkout` 检出的是**触发那一刻的 SHA**，可能已经落后于 `origin/main`；
2. 这一轮又改了 `site/data/version.json`（**时间戳每次都变 → 必然冲突**）；
3. `git pull --rebase origin main || true` → rebase 冲突，**但 `|| true` 把失败吞掉了**；
4. 仓库停在「rebase 中」，**HEAD 变成游离态（detached HEAD）**；
5. 随后的 `git push` 报 `fatal: You are not currently on a branch` → **退出码 128**；
6. 而 `|| true` 让第 3 步看着像成功了，**日志里毫无线索**。

**修复（不用 rebase）**：只碰数据文件的提交，用「回到远端最新 + 精确搬回自己的产物」：

```bash
git add site/data && git commit -m "..."
BAKE_COMMIT="$(git rev-parse HEAD)"
git fetch origin "$BRANCH"
git reset --hard "origin/$BRANCH"
git checkout "$BAKE_COMMIT" -- site/data
git add site/data
git commit -m "..."
git push origin "HEAD:$BRANCH"
```

只动 `site/data` → 不存在冲突面；且远端别人的其它改动**原样保留**。

**通用教训**：
1. **`|| true` 吞掉中间步骤的失败是最坏的 CI 写法** ——
   它把「有问题的状态」留给后续步骤，让真正的错误出现在一个**看起来毫不相关**的地方。
2. **`actions/checkout` 检出的是触发时的 SHA，不是最新 main** ——
   凡是「检出后还要提交并推送」的工作流，都必须假设 HEAD 可能落后于远端。
3. **「每次都变的时间戳文件」是 rebase 冲突的天然磁铁** ——
   机器产物（version.json / 锁文件 / 构建清单）几乎必然冲突，别指望 rebase 能自动合上。

## 5. 多镜像探测的失败退避与探测节奏

| 项 | 取值 | 理由 |
|---|---|---|
| 探测周期 | 60 秒 | CI 每 20 分钟更新一次数据 |
| 失败退避 | 1 次→1 分钟，2 次→5 分钟，3 次+→30 分钟 | 别让唯一新鲜的源因为偶发失败被冷落半小时 |
| 成功 | 立即清零失败计数 | |
| 单镜像超时 | 3500ms（版本探测）/ 6000ms（正文抓取） | 超时必须真的触发，不能被后台标签页节流 |
| 陈旧上限 | liverooms 75 分钟；schedule / catalog 24 小时 | 见 §3.3 |

**验收判据要跟着改**：先在 Node 侧独立问上游「现在有没有直播信号」，
上游在播却显示不出来 **且** 没有告知通道故障，才算失败；
上游本来就没信号时，判据改成「必须如实标注无信号」。

## 6. 镜像可达性必须在浏览器里测

Node 的网络路径和浏览器不同：

- 本机 Chrome 直接 fetch `raw.githubusercontent.com` → **8ms `Failed to fetch`**
- 同一台机器上走系统代理的 PowerShell / `Invoke-WebRequest` → **1062ms 拿到 200**

→ 「我用命令行能拉到」**推不出**「用户浏览器能拉到」。
→ 镜像可达性要在**浏览器里**实测（`tools/probe-mirrors.mjs` / `probe-mirrors2.mjs`）。

另外记一笔：`data.jsdelivr.com/v1/packages/gh/<repo>@main/resolved` 返回 400、
